- Retry loading listening history.

ERROR HANDLING RULES

- Use Android ConnectivityManager / NetworkCapabilities as an initial connectivity hint, not as proof that the Supabase server is reachable.
- Handle actual HTTP/network exceptions and Supabase response errors.
- Distinguish network errors, timeouts, server errors, authentication/session errors, permission errors, and user-input validation errors.
- Show this connection/server modal for connection and server availability failures.
- Do not show this generic modal for normal validation errors, incorrect passwords, cancelled Google OAuth, or expected user actions. Show a relevant inline message or specific error instead.
- Avoid showing repeated stacked dialogs for multiple failures. Update or reuse the existing modal.
- Do not show the modal for every background polling failure; use sensible retry/backoff and surface errors when they affect a user-requested action.
- Do not expose raw stack traces, access tokens, database internals, or sensitive server responses to users.
- Log useful diagnostic details safely for debugging, without logging secrets.
- If the user is offline, explain that an internet connection is required for the requested cloud operation.
- If the server is unavailable, let the user retry later.
- Keep locally available UI usable where possible even when cloud services are unavailable.
